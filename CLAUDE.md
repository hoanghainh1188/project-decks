# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

ProjectDesk is a Microsoft Project–style scheduling app for macOS built with Tauri 2, React 19, and Rust. The UI is in Vietnamese and English (see Languages below); the README and the plan doc are in Vietnamese.

## Commands

```bash
pnpm install
pnpm tauri dev                          # run the desktop app (Vite on :1420 + Rust shell)
pnpm build                              # tsc + vite build (frontend only)
pnpm exec tsc --noEmit                  # typecheck
pnpm test                               # frontend tests (Vitest, jsdom)
pnpm test src/viewRows.test.ts          # a single frontend test file (add -t "<name>" for one case)
cargo test -p projectdesk-engine        # engine tests
cargo test -p projectdesk-engine <name> # engine tests whose name matches the filter
cargo bench -p projectdesk-engine --bench large_project            # apply/undo/save/open timings, 1,000 tasks and 10,000 commands
cargo bench -p projectdesk-engine --bench large_project -- 300 1200  # same with <tasks> <commands>
cargo bench -p projectdesk-engine --bench large_project -- leveling   # leveling 500 tasks on 10 people
```

CI (`.github/workflows/ci.yml`) runs the engine tests, the typecheck, and `pnpm test`. `.github/workflows/build.yml` builds unsigned installers for macOS, Windows, and Linux. It runs on `v*` tags, which also create a draft release, on manual dispatch, and on PRs that touch the Rust code, `package.json`, or the lockfiles. The real UI only works inside Tauri: `inTauri()` guards every `invoke`, so a plain browser at `localhost:1420` can't load project state.

## Architecture

Cargo workspace with two members: `crates/engine` (pure Rust, no Tauri dependency) and `src-tauri` (thin IPC shell). The React app lives in `src/`.

**The engine is the source of truth.** The UI never computes dates, slack, the critical path, costs, EVM, or burn-down numbers. It sends a `Command` and renders the `Snapshot` it gets back.

- **Time model** (`crates/engine/src/lib.rs`, `timeutil.rs`): instants are Unix milliseconds holding *project wall-clock time* formatted as UTC (no timezone conversion). Durations, lags, and work are **working minutes**. `Calendar` converts between the two.
- **Command log and undo** (`command.rs`, `document.rs`): every edit is a variant of the serde-tagged `Command` enum (`#[serde(tag = "type", rename_all = "snake_case")]`). `Document::apply` runs `apply_one` on a clone, then `schedule()`, and commits only if both succeed. Undo and redo **replay** `base` plus `commands[..cursor]` instead of reversing anything, so every command must be deterministic and replayable from the base project.
- **Checkpoints** (`checkpoint.rs`): `Document::project_at` replays from the nearest cached scheduled state instead of from `base`. `apply` and replays keep one every `INTERVAL` (25) commands; memory holds at most 24, dense near the present with sparse anchors further back. A checkpoint is only a cache: `apply` drops the ones past the cursor when it truncates the log. Files store the checkpoint at the cursor plus three below it, tagged with `engine_tag()` (crate version plus `ENGINE_REVISION`); `load` uses only matching ones and replays otherwise. **Bump `ENGINE_REVISION` whenever an engine change can move dates or derived fields for the same commands.**
- **Scheduling** (`schedule.rs`): `schedule()` runs after every command. It normalizes the outline/WBS, builds a `Graph` (`graph.rs`: UID → position, subtrees, links per task, leaf order; a link to or from a summary goes through one virtual node instead of every leaf pair), which also detects cycles, runs forward/backward CPM passes (with a few passes for summary finish constraints), then rolls up summaries and publishes derived fields: free slack, costs and usage (`work.rs`), overallocations (`level.rs`), predecessor text, and the late flag. Derived fields live on the model structs and are overwritten on every schedule run.
- **Persistence** (`store.rs`): a `.pdproj` file is SQLite with `meta` (version, cursor, base project JSON), `command_log` (serialized commands), and `burndown`. On load (`store::open`) the engine replays the log from the nearest checkpoint. A command that does not parse, is unknown (likely from a newer app), or fails to apply does not stop the open: `open` returns an unsaved copy (`path` None, `dirty`) at the last state it can rebuild (a later checkpoint this engine saved, else the replayed prefix with its undo history), Damage only in the redo commands after the cursor opens the file itself and drops those commands on the next save. A damaged cursor or burn-down table also opens. `open` returns an `OpenReport` (`recovery.rs`) whose `message()` the Tauri layer shows as a warning sheet. The report also lists tasks whose dates differ from a checkpoint another engine saved at the cursor. `load` is `open` without the report. Burn-down snapshots sit outside the command log on purpose, so undo doesn't remove them. `save` writes a new, uniquely named hidden temp file beside the real file (following a symlink) in one transaction, keeps the old file's permissions, and renames it over the file, so a crash never leaves a half-written project. `load` refuses files whose `version` is above `FORMAT_VERSION`. **Bump `FORMAT_VERSION` whenever you add a `Command` variant or a table an older app must read**, because an older app replaying the log cannot read commands it doesn't know. The `checkpoint` table is a cache older apps ignore, so it did not need a bump.
- **Autosave and history** (`autosave.rs`, `Document::compact_history`): a background thread in the Tauri layer writes unsaved changes every 30 s to one slot in the app data folder (`autosave.pdproj` plus a JSON note naming the original file). Saving, discarding, replacing the document, or quitting clears it. On launch the frontend calls `check_autosave`, which offers the slot back; a restored project is unsaved changes to its original path. "Gộp lịch sử hoàn tác" (`compact_history`) folds all but the last 100 undo steps into `base`; it is not a `Command` and cannot be undone.
- **Overallocation and leveling** (`level.rs`): a resource is overallocated when, at some instant, the units of the assignments working then exceed what it has (its max units while its calendar works, else none); work counts only inside the task calendar's ranges and segments, so tasks at different hours of one day do not clash. Leveling is serial: tasks it cannot move (manual, started, MSO/MFO) first, then earliest start, higher priority, less slack; each goes to the first moment all its resources have room, and placed tasks never move again. `schedule()` is split into `prepare` (graph), `schedule_dates`, and `publish_derived`, so leveling builds the graph once and only reschedules dates. `Document::apply` logs `LevelResources` as `ApplyLeveling { delays }`, so replay never reruns the heuristic.
- **MSPDI** (`mspdi.rs`): XML import/export for Microsoft Project interop. There is no `.mpp` reader. Importing replaces the document (`replace_project`), which clears history.
- **Tracking** (`tracking.rs`): actual progress follows Microsoft Project. An actual start pins the start over links, constraints, leveling, and manual dates; an actual finish pins the finish; without one the remaining work runs on from the actual start. Complete tasks (and groups) are never critical, a started task's slack is measured at its finish, and leveling skips started tasks. Remaining duration/work edits keep the done part. `late` from the status date means less is done than the schedule says is due by then (`behind_schedule`). The tracking commands live here, called from `command.rs`, including `RescheduleUncompleted` (split a started task at its progress point so the rest resumes at the status date; SNET on the status date for tasks that should have started). Recording progress on a recurring occurrence does not detach it, and regenerating a series keeps occurrences with progress. A background series (`RecurrenceSpec::background`) never sets the project finish or the critical path. EVM phases actuals over the task's segments (`evm::progress_intervals`).
- **Split tasks** (`split.rs`): a split stores work offsets and gaps; `schedule()` derives the dated `segments`. Baselines keep their own segments, and PV skips split gaps (`evm::worked_fraction`).
- **Network diagram** (`network.rs`): the engine lays out the boxes and edge routes. A recurring series is one box (its summary); with summaries hidden, a link to or from a summary is drawn to the tasks that end or start the group, so an edge's `from_uid`/`to_uid` are the boxes joined, not always the link's own tasks. The `network_layout` Tauri command returns them and the UI only draws.
- **Tauri layer** (`src-tauri/src/lib.rs`): holds `Mutex<Document>`, exposes the commands wrapped by `src/api.ts`. `apply_command`, `undo`, `redo` and the large reads are `#[tauri::command(async)]`, so they run on the thread pool, not the main thread; `src/api.ts` therefore sends them one at a time (`inOrder`), and file commands wait for queued edits (`afterQueued`) without holding later calls behind their dialog. It also builds the native macOS menu, which sends `menu-action` events to the frontend. File dialogs must use the plugin's non-blocking `pick_file`/`save_file` through `await_pick`/`await_save`. `blocking_pick_file` deadlocks on the macOS main thread. The `dialog_open` flag stops two dialogs from opening at once. `apply_command`, `undo` and `redo` refuse while a dialog is open. Any command that replaces the document (new, open, import) must call `confirm_discard` while holding that permit. It asks "Lưu / Không lưu / Hủy" when there are unsaved changes. Build alerts with `alert()`, which attaches them to the main window as a sheet. Without a parent window, rfd falls back to a system notification on macOS that answered with the default button on its own when tested. Closing the window, Cmd+Q (a custom `quit` menu item, not the predefined one), and quitting from the Dock all go through `quit_if_confirmed`.
- **Frontend** (`src/`): `types.ts` is a **hand-written mirror** of the Rust serde types, including the `Command` union. When you add or change a `Command` variant or a model field in Rust, update `types.ts` to match. `App.tsx` owns snapshot state and menu handling. Keyboard shortcuts and menu accelerators both go through `dispatchAction`, which acts once per key press. `shouldRunAction` (`shortcuts.ts`) sends undo and redo to a focused field only while it holds uncommitted typing, and Cmd+Backspace in a field always edits text; `runFieldAction` does those field edits, because the native menu takes the key first. `viewRows.ts` does filter, group, and highlight on the client side as a view-only transform. `Toolbar.tsx` (task, project, and report commands in groups, with `MenuButton.tsx` for the "Thêm việc ▾" and "Liên kết ▾" menus) sits above `ViewBar.tsx` (view tabs and per-view controls). `toolbarState.ts` decides whether each command can run and gives the reason shown as its tooltip; `handleMenu` uses the same states for the native menu, so add a check there rather than in a button. The link commands pair the selected task with the task above it in outline order (`taskAbove`), not the row above on screen. Toolbar buttons take a colour by group from the `--tone-*` tokens in `styles.css`; dialog and panel buttons use `Button.tsx` (primary, secondary, danger). Icons come from `lucide-react` and are `aria-hidden`, so the text stays the accessible name. Every dialog uses `Modal.tsx` (`aria-modal`, a fixed header with a ✕ and a fixed `footer` for its buttons around a scrolling body, focus in and back, Tab kept inside, Escape and the backdrop commit the focused field and close); while one is open `shouldRunAction` lets only undo, redo, and save through, so build new dialogs on it. "Thông tin dự án" is a transaction: it records `Snapshot.history_cursor` when it opens, edits apply live, and Hủy undoes back to that cursor (`undoTo.ts`); undo inside it stops at that point. `ganttKeys.ts` maps keys on the focused Gantt to select, move, resize, or edit; Alt+arrows ask for the next working day on the task's calendar and the engine still schedules the result. `ganttLayout.ts` and `GanttChart.tsx` render the Gantt. Set fonts with `var(--font-ui)` in CSS and `UI_FONT_FAMILY` (`uiFont.ts`) on canvases, never `-apple-system` alone: Chromium webviews can then render Vietnamese stacked marks (ế) apart from the letter. `ganttPdf.ts` exports it to PDF with jsPDF and the embedded Be Vietnam Pro font (`src/fonts/`), which provides the Vietnamese glyphs.

## Languages

The interface speaks Vietnamese (`vi`, the original) and English (`en`). Every user-facing string goes through a catalog; never write UI text inline.

- **Frontend** (`src/i18n/`): each area has a colocated catalog, `<Name>.i18n.ts`, made with `defineMessages(vi, en)`. `en` is typed from `vi`, so a missing key or a different function signature is a type error. Components read it with `useMessages(catalog)`; plain modules (PDF export, labels, `toolbarState`) use `pick(catalog)`, which reads the current language. Messages that take values are functions. `I18nProvider` sets the language that `format.ts` reads: Vietnamese shows `05/01/2026 08:00`, `7,5 ngày`, `3.480.000`; English shows `2026-01-05 08:00`, `7.5 days`, `3,480,000`. Parsers accept both forms in either language. Tests run in Vietnamese unless they wrap in `<I18nProvider lang="en">` or call `setCurrentLang("en")`, and must reset to `vi` afterwards.
- **Choosing the language**: `Root.tsx` loads the remembered choice (`get_language`), or follows `navigator.languages` without storing it, before the first render, and tells the backend with `set_language(lang, remember)`. View → Language (`lang-vi` / `lang-en` menu ids) switches and remembers it in `settings.json` in the app config dir (`src-tauri/src/settings.rs`).
- **Rust**: the shell's strings (menu, dialogs, alerts, About) live in `src-tauri/src/i18n.rs`; `set_language` rebuilds the native menu. The engine has `Lang` (`crates/engine/src/lang.rs`); `EngineError::message(lang)` and `OpenReport::message(lang)` give user-facing text, and `Display` stays Vietnamese. Names the engine writes into a project (default task, calendar and resource names) are data and stay as they are, so replay and saved files do not depend on the language.

## Tests

- **Engine:** integration tests in `crates/engine/tests/`. `engine.rs` covers the core; `limits.rs` covers the follow-ups to phases 9–10 (recurrence patterns, series units, older files, time-phased AC, S-curve); `split.rs` covers split tasks; `store.rs` covers atomic saves and format versions; `checkpoint.rs` checks that undo, redo, and open from checkpoints match a full replay; `recovery.rs` covers damaged logs and the moved-task report; `autosave.rs` covers the autosave slot and history compaction; `tracking.rs` checks actual-date scheduling against hand-computed dates; `leveling.rs` covers hour-level overallocation and leveling; `progress.rs` covers rescheduling, split-task actual cost, and recurring progress. The network layout has unit tests inside `network.rs`. `cargo test -p projectdesk` runs the few Tauri-layer unit tests (not in CI). Fixtures use `at(day_offset, hour, minute)`, based on Monday 2026-01-05. The default calendar is Mon–Fri, 08:00–12:00 and 13:00–17:00, so one working day is 480 minutes.
- **Frontend:** `src/**/*.test.{ts,tsx}` with Vitest and Testing Library. `src/test/setup.ts` mocks `@tauri-apps/api/core` and `@tauri-apps/api/event`, so `invoke` goes to `src/test/fakeBackend.ts`. That fake records calls and applies a few commands in memory; it does not run the engine. Use `fakeBackend.reset(...)` and `failNext(...)` with the builders in `src/test/fixtures.ts`. If a component sends a command the fake doesn't handle yet, extend the fake.
