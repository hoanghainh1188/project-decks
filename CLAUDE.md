# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Sheafly is a Microsoft Project–style scheduling app for macOS, Windows and Linux, built with Tauri 2, React 19, and Rust. The UI is in Vietnamese and English (see Languages below). `README.md` is in English and `README.vi.md` in Vietnamese; keep them in step. The plan doc is in Vietnamese.

## Commands

```bash
pnpm install
pnpm tauri dev                          # run the desktop app (Vite on :1420 + Rust shell)
pnpm build                              # tsc + vite build (frontend only)
pnpm exec tsc --noEmit                  # typecheck
pnpm test                               # frontend tests (Vitest, jsdom)
pnpm test src/viewRows.test.ts          # a single frontend test file (add -t "<name>" for one case)
cargo test -p sheafly-engine        # engine tests
cargo test -p sheafly-engine <name> # engine tests whose name matches the filter
cargo bench -p sheafly-engine --bench large_project            # apply/undo/save/open timings, 1,000 tasks and 10,000 commands
cargo bench -p sheafly-engine --bench large_project -- 300 1200  # same with <tasks> <commands>
cargo bench -p sheafly-engine --bench large_project -- leveling   # leveling 500 tasks on 10 people
```

The webview runs under a CSP (`app.security.csp` in `tauri.conf.json`): scripts only from the app, inline styles allowed (components use `style={…}`), images and fonts also from `data:`/`blob:` (canvas and jsPDF). A new feature that loads anything else (a remote font, `eval`, a worker) needs the policy widened, and checked against the production build. CI (`.github/workflows/ci.yml`) runs the engine tests, the typecheck, and `pnpm test`. `.github/workflows/build.yml` builds unsigned installers for macOS (universal: Apple Silicon and Intel), Windows, and Linux. It runs on `v*` tags, which also create a draft release, on manual dispatch, and on PRs that touch the Rust code, `package.json`, or the lockfiles. The real UI only works inside Tauri: `inTauri()` guards every `invoke`, so a plain browser at `localhost:1420` can't load project state.

## Architecture

Cargo workspace with two members: `crates/engine` (pure Rust, no Tauri dependency) and `src-tauri` (thin IPC shell). The React app lives in `src/`.

**The engine is the source of truth.** The UI never computes dates, slack, the critical path, costs, EVM, or burn-down numbers. It sends a `Command` and renders the `Snapshot` it gets back.

- **Time model** (`crates/engine/src/lib.rs`, `timeutil.rs`): instants are Unix milliseconds holding *project wall-clock time* formatted as UTC (no timezone conversion). Durations, lags, and work are **working minutes**. `Calendar` converts between the two.
- **Command log and undo** (`command.rs`, `document.rs`): every edit is a variant of the serde-tagged `Command` enum (`#[serde(tag = "type", rename_all = "snake_case")]`). `Document::apply` runs `apply_one` on a clone, then `schedule()`, and commits only if both succeed. Undo and redo **replay** `base` plus `commands[..cursor]` instead of reversing anything, so every command must be deterministic and replayable from the base project.
- **Checkpoints** (`checkpoint.rs`): `Document::project_at` replays from the nearest cached scheduled state instead of from `base`. `apply` and replays keep one every `INTERVAL` (25) commands; memory holds at most 24, dense near the present with sparse anchors further back. A checkpoint is only a cache: `apply` drops the ones past the cursor when it truncates the log. Files store the checkpoint at the cursor plus three below it, tagged with `engine_tag()` (crate version plus `ENGINE_REVISION`); `load` uses only matching ones and replays otherwise. **Bump `ENGINE_REVISION` whenever an engine change can move dates or derived fields for the same commands.**
- **Scheduling** (`schedule.rs`): `schedule()` runs after every command. It normalizes the outline/WBS, builds a `Graph` (`graph.rs`: UID → position, subtrees, links per task, leaf order; a link to or from a summary goes through one virtual node instead of every leaf pair), which also detects cycles, runs forward/backward CPM passes (with a few passes for summary finish constraints), then rolls up summaries and publishes derived fields: free slack, costs and usage (`work.rs`), overallocations (`level.rs`), predecessor text, and the late flag. Derived fields live on the model structs and are overwritten on every schedule run.
- **Persistence** (`store.rs`): a `.sheafly` file (`.pdproj` before the rename from ProjectDesk; both open, saves default to `.sheafly`) is SQLite with `meta` (version, cursor, base project JSON), `command_log` (serialized commands), and `burndown`. On load (`store::open`) the engine replays the log from the nearest checkpoint. A command that does not parse, is unknown (likely from a newer app), or fails to apply does not stop the open: `open` returns an unsaved copy (`path` None, `dirty`) at the last state it can rebuild (a later checkpoint this engine saved, else the replayed prefix with its undo history), Damage only in the redo commands after the cursor opens the file itself and drops those commands on the next save. A damaged cursor or burn-down table also opens. `open` returns an `OpenReport` (`recovery.rs`) whose `message()` the Tauri layer shows as a warning sheet. The report also lists tasks whose dates differ from a checkpoint another engine saved at the cursor. `load` is `open` without the report. Burn-down snapshots sit outside the command log on purpose, so undo doesn't remove them. `save` writes a new, uniquely named hidden temp file beside the real file (following a symlink) in one transaction, keeps the old file's permissions, and renames it over the file, so a crash never leaves a half-written project. `load` refuses files whose `version` is above `FORMAT_VERSION`. **Bump `FORMAT_VERSION` whenever you add a `Command` variant or a table an older app must read**, because an older app replaying the log cannot read commands it doesn't know. The `checkpoint` table is a cache older apps ignore, so it did not need a bump.
- **Autosave and history** (`autosave.rs`, `Document::compact_history`): a background thread in the Tauri layer writes unsaved changes every 30 s to one slot in the app data folder (`autosave.pdproj` plus a JSON note naming the original file). Saving, discarding, replacing the document, or quitting clears it. On launch the frontend calls `check_autosave`, which offers the slot back; a restored project is unsaved changes to its original path. "Gộp lịch sử hoàn tác" (`compact_history`) folds all but the last 100 undo steps into `base`; it is not a `Command` and cannot be undone.
- **Overallocation and leveling** (`level.rs`): a resource is overallocated when, at some instant, the units of the assignments working then exceed what it has (its max units while its calendar works, else none); work counts only inside the task calendar's ranges and segments, so tasks at different hours of one day do not clash. Leveling is serial: tasks it cannot move (manual, started, MSO/MFO) first, then earliest start, higher priority, less slack; each goes to the first moment all its resources have room, and placed tasks never move again. `schedule()` is split into `prepare` (graph), `schedule_dates`, and `publish_derived`, so leveling builds the graph once and only reschedules dates. `Document::apply` logs `LevelResources` as `ApplyLeveling { delays }`, so replay never reruns the heuristic.
- **MSPDI** (`mspdi.rs`): XML import/export for Microsoft Project interop. There is no `.mpp` reader. Importing replaces the document (`replace_project`), which clears history.
- **Tracking** (`tracking.rs`): actual progress follows Microsoft Project. An actual start pins the start over links, constraints, leveling, and manual dates; an actual finish pins the finish; without one the remaining work runs on from the actual start. Complete tasks (and groups) are never critical, a started task's slack is measured at its finish, and leveling skips started tasks. Remaining duration/work edits keep the done part. `late` from the status date means less is done than the schedule says is due by then (`behind_schedule`). The tracking commands live here, called from `command.rs`, including `RescheduleUncompleted` (split a started task at its progress point so the rest resumes at the status date; SNET on the status date for tasks that should have started). Recording progress on a recurring occurrence does not detach it, and regenerating a series keeps occurrences with progress. A background series (`RecurrenceSpec::background`) never sets the project finish or the critical path. EVM phases actuals over the task's segments (`evm::progress_intervals`).
- **Split tasks** (`split.rs`): a split stores work offsets and gaps; `schedule()` derives the dated `segments`. Baselines keep their own segments, and PV skips split gaps (`evm::worked_fraction`). `MoveSegment` drags segment 1 or later by setting the gap before it (later segments move along; a closed gap joins the two); segment 0 moves with the task.
- **Copy, paste, fill-down** (`clipboard.rs`): `copy_tasks` (a Tauri read, not a command) turns the selected tasks and their subtrees into a `TaskClipboard` that holds the data itself (name, relative level, duration, work, manual dates, notes, priority, calendar, constraint, deadline, task type, fixed cost, splits, assignments, links between copied tasks; not progress, baselines, leveling delay or recurrence), so `PasteTasks` replays without the originals. Paste goes after the anchor's subtree (after the whole series for an occurrence) and matches resources and calendars by UID and name, then by name. `FillDown` applies the cell's own edit command (`apply_one`) to each target in one undo step; one failing row (a cycle from predecessors) fails the whole fill.
- **Network diagram** (`network.rs`): the engine lays out the boxes and edge routes. A recurring series is one box (its summary); with summaries hidden, a link to or from a summary is drawn to the tasks that end or start the group, so an edge's `from_uid`/`to_uid` are the boxes joined, not always the link's own tasks. The `network_layout` Tauri command returns them and the UI only draws.
- **Tauri layer** (`src-tauri/src/lib.rs`): holds `Mutex<Document>`, exposes the commands wrapped by `src/api.ts`. `apply_command`, `undo`, `redo` and the large reads are `#[tauri::command(async)]`, so they run on the thread pool, not the main thread; `src/api.ts` therefore sends them one at a time (`inOrder`), and file commands wait for queued edits (`afterQueued`) without holding later calls behind their dialog. It also builds the native macOS menu, which sends `menu-action` events to the frontend. File dialogs must use the plugin's non-blocking `pick_file`/`save_file` through `await_pick`/`await_save`. `blocking_pick_file` deadlocks on the macOS main thread. The `dialog_open` flag stops two dialogs from opening at once. `apply_command`, `undo` and `redo` refuse while a dialog is open. Any command that replaces the document (new, open, import) must call `confirm_discard` while holding that permit. It asks "Lưu / Không lưu / Hủy" when there are unsaved changes. Build alerts with `alert()`, which attaches them to the main window as a sheet. Without a parent window, rfd falls back to a system notification on macOS that answered with the default button on its own when tested. Closing the window, Cmd+Q (a custom `quit` menu item, not the predefined one), and quitting from the Dock all go through `quit_if_confirmed`. **Opening files:** Open…, File → Open Recent (`recent:<index>` menu ids → `open_recent`) and files the system sends all end in `open_path_held`, after the permit and `confirm_discard`; it also records the file in the recent list (`settings.json`, ten entries, rebuilt into the menu by `refresh_menu`), as saving does. `bundle.fileAssociations` registers `.sheafly` and `.pdproj`. macOS delivers a double-clicked file as `RunEvent::Opened`; Windows and Linux pass it on the command line, and `tauri-plugin-single-instance` forwards a second launch's file to the running app. Such a file waits in `pending_open` and the frontend opens it with `open_pending` when no dialog is up (at launch, after the autosave offer).
- **Frontend** (`src/`): `types.ts` is a **hand-written mirror** of the Rust serde types, including the `Command` union. When you add or change a `Command` variant or a model field in Rust, update `types.ts` to match. `App.tsx` owns snapshot state; `menuActions.ts` (`handleMenuAction`) maps a native menu id or shortcut to its action, `useFileDialog.ts` runs one native file dialog at a time and opens a file the system sent once it is free, and `ProjectDialog`, `BaselineDialog` and `StatusBar` are their own components. Keyboard shortcuts and menu accelerators both go through `dispatchAction`, which acts once per key press. `shouldRunAction` (`shortcuts.ts`) sends undo and redo to a focused field only while it holds uncommitted typing, and Cmd+Backspace in a field always edits text; `runFieldAction` does those field edits, because the native menu takes the key first. `viewRows.ts` does filter, group, and highlight on the client side as a view-only transform. `Toolbar.tsx` (task, project, and report commands in groups, with `MenuButton.tsx` for the "Thêm việc ▾" and "Liên kết ▾" menus) sits above `ViewBar.tsx` (view tabs and per-view controls). `toolbarState.ts` decides whether each command can run and gives the reason shown as its tooltip; `handleMenuAction` uses the same states for the native menu, so add a check there rather than in a button. The link commands pair the selected task with the task above it in outline order (`taskAbove`), not the row above on screen. Toolbar buttons take a colour by group from the `--tone-*` tokens; dialog and panel buttons use `Button.tsx` (primary, secondary, danger). Icons come from `lucide-react` and are `aria-hidden`, so the text stays the accessible name. Every dialog uses `Modal.tsx` (`aria-modal`, a fixed header with a ✕ and a fixed `footer` for its buttons around a scrolling body, focus in and back, Tab kept inside, Escape and the backdrop commit the focused field and close); while one is open `shouldRunAction` lets only undo, redo, save, language and theme through (`MODAL_ACTIONS`), so build new dialogs on it. "Thông tin dự án" is a transaction: it records `Snapshot.history_cursor` when it opens, edits apply live, and Hủy undoes back to that cursor (`undoTo.ts`); undo inside it stops at that point. **Copy, paste, fill-down:** Edit has the native Cut/Copy/Paste/Select All, so text fields keep their own clipboard; outside a field (and with no page text selected) the webview's `copy`/`paste` events copy and paste tasks (`useClipboardEvents.ts`; cancelling `beforecopy`/`beforepaste` enables the items in WebKit). Edit → Copy Task (⌘⌥C), Paste Task (⌘⌥V) and Fill Down (⌘D) are menu ids `copy-task`, `paste-task`, `fill-down`, gated by `toolbarState.ts`. The clipboard lives in App state. Shift+click in the sheet sets `selectionEnd`; `selectionRange` (`taskSelection.ts`) gives the rows in screen order; the column of the last focused sheet cell (`SheetColumn.fill`) picks the fill field. `ganttKeys.ts` maps keys on the focused Gantt to select, move, resize, or edit; Alt+arrows ask for the next working day on the task's calendar and the engine still schedules the result. `ganttLayout.ts` and `GanttChart.tsx` render the Gantt. **Colours and themes:** every colour is a token in `src/tokens.css` (`--surface*`, `--text*`, `--border*`, `--grid`, `--weekend`, `--bar-*`, `--chart-*`, `--tone-*`, …), light on `:root` and dark on `:root[data-theme="dark"]`; never write a colour literal in `styles.css` or a component. `theme.ts` resolves View → Appearance (System, Light, Dark; `get_theme`/`set_theme`, remembered in `settings.json`) and sets `data-theme` on `<html>`; Root applies the saved choice before the first render. SVG views use `style={{ fill: "var(--token)" }}` (not the `fill` attribute). A canvas cannot read `var()`: read `canvasPalette()` (add the colour to `CANVAS_TOKENS` with its light value) and repaint when `useResolvedTheme()` changes, as `GanttChart.tsx` does. PDF export stays light (`barColor` defaults to `LIGHT_CANVAS`). `theme.test.ts` checks that every token exists in both themes and that text keeps 4.5:1 contrast on the surfaces it sits on; add a pair there for a new text colour. Set fonts with `var(--font-ui)` in CSS and `UI_FONT_FAMILY` (`uiFont.ts`) on canvases, never `-apple-system` alone: Chromium webviews can then render Vietnamese stacked marks (ế) apart from the letter. `ganttPdf.ts` exports it to PDF with jsPDF (page layout in `ganttPageGrid`, shared drawing helpers in `pdfDraw.ts`) and the embedded Be Vietnam Pro font (`src/fonts/`), which provides the Vietnamese glyphs.

## Languages

The interface speaks Vietnamese (`vi`, the original) and English (`en`). Every user-facing string goes through a catalog; never write UI text inline.

- **Frontend** (`src/i18n/`): each area has a colocated catalog, `<Name>.i18n.ts`, made with `defineMessages(vi, en)`. `en` is typed from `vi`, so a missing key or a different function signature is a type error. Components read it with `useMessages(catalog)`; plain modules (PDF export, labels, `toolbarState`) use `pick(catalog)`, which reads the current language. Messages that take values are functions. `I18nProvider` sets the language that `format.ts` reads: Vietnamese shows `05/01/2026 08:00`, `7,5 ngày`, `3.480.000`; English shows `2026-01-05 08:00`, `7.5 days`, `3,480,000`. Parsers accept both forms in either language. Tests run in Vietnamese unless they wrap in `<I18nProvider lang="en">` or call `setCurrentLang("en")`, and must reset to `vi` afterwards.
- **Choosing the language**: `Root.tsx` loads the remembered choice (`get_language`), or follows `navigator.languages` without storing it, before the first render, and tells the backend with `set_language(lang, remember)`. View → Language (`lang-vi` / `lang-en` menu ids) switches and remembers it in `settings.json` in the app config dir (`src-tauri/src/settings.rs`).
- **Rust**: the shell's strings (menu, dialogs, alerts, About) live in `src-tauri/src/i18n.rs`; `set_language` rebuilds the native menu. The engine has `Lang` (`crates/engine/src/lang.rs`); `EngineError::message(lang)` and `OpenReport::message(lang)` give user-facing text, and `Display` stays Vietnamese. Names written into a project are data and never change with the language, so replay and saved files do not depend on it. Default names are chosen when an item is created: the UI sends localized names for new tasks, resources, milestones and calendars, and `Document::new_in(lang)` names a new project, its first task and calendar. The untouched project made at launch is renamed when `set_language` runs. Predecessor text the UI sends is normalized (`normalizePredecessorText`) to lag units the engine reads, so files stay readable by older apps. English date input accepts only ISO (`2026-01-05`).

## Third-party licenses

The installers ship `src-tauri/THIRD_PARTY_LICENSES.txt` (`bundle.resources`), and Help → Third-Party Licenses opens it (`open_third_party_licenses`). `scripts/third-party-licenses.mjs` builds it from the license files of every shipped npm package (`pnpm licenses list --prod`) and Rust crate (normal dependencies of `sheafly` on any platform, from `cargo metadata`), plus the Be Vietnam Pro OFL; a package with no license file gets the SPDX text in `scripts/license-texts/`. **Run it after adding or updating a dependency** and commit the result: CI runs it with `--check` and fails when the file is stale. Before adding a dependency, check its license is permissive (MIT, Apache-2.0, BSD, ISC, Zlib, Unicode, OFL for fonts; MPL-2.0 only unmodified); no GPL or AGPL.

## Tests

- **Engine:** integration tests in `crates/engine/tests/`. `engine.rs` covers the core; `limits.rs` covers the follow-ups to phases 9–10 (recurrence patterns, series units, older files, time-phased AC, S-curve); `split.rs` covers split tasks; `clipboard.rs` covers copy/paste, fill-down and dragging a segment; `store.rs` covers atomic saves and format versions; `checkpoint.rs` checks that undo, redo, and open from checkpoints match a full replay; `recovery.rs` covers damaged logs and the moved-task report; `autosave.rs` covers the autosave slot and history compaction; `tracking.rs` checks actual-date scheduling against hand-computed dates; `leveling.rs` covers hour-level overallocation and leveling; `progress.rs` covers rescheduling, split-task actual cost, and recurring progress. The network layout has unit tests inside `network.rs`. `cargo test -p sheafly` runs the few Tauri-layer unit tests (not in CI). Fixtures use `at(day_offset, hour, minute)`, based on Monday 2026-01-05. The default calendar is Mon–Fri, 08:00–12:00 and 13:00–17:00, so one working day is 480 minutes.
- **Frontend:** `src/**/*.test.{ts,tsx}` with Vitest and Testing Library. `src/test/setup.ts` mocks `@tauri-apps/api/core` and `@tauri-apps/api/event`, so `invoke` goes to `src/test/fakeBackend.ts`. That fake records calls and applies a few commands in memory; it does not run the engine. Use `fakeBackend.reset(...)` and `failNext(...)` with the builders in `src/test/fixtures.ts`. If a component sends a command the fake doesn't handle yet, extend the fake.
